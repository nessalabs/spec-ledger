# Give concurrent work distinct identities

Agents working in separate checkouts currently allocate the same numbered workstream, turn and claim IDs. Integrating the experiment and workflow-library branches has produced real collisions. People should name work with a short title; Spec Ledger must generate its identity.

The user explicitly requests UUID identities, migration of existing data, no numbered-ID compatibility, reconciliation of both branches, and an organization-wide npm publishing credential. This is scoped implementation and migration authorization. Retain the existing library/staging quality bar and correctness-critical provenance guarantees.

## Behavior

Every independently created ledger entity receives a generated UUID from the owning shared operation. Agent inputs supply titles, statements or descriptions, never a chosen persistent ID. Returned IDs remain the unambiguous reference for subsequent operations; duplicate titles are valid. Workstreams, turns, claims, proposed claims, bindings, episode records, reviews, goals, attempts, workflows, authority, compass records and automation records follow the same identity rule. Nested slice and finding identities must also avoid counter allocation. Graph feature/node keys are authored architectural vocabulary, not independently minted work episodes, and remain named keys. Revision numbers, acceptance positions and attempt ordinals remain numbers because they represent ordering, not global identity.

Creation must publish without overwriting another record, including concurrent writes and operation retries. UUIDs do not replace existing permission, snapshot, evidence or lock semantics. Caller-stable request IDs remain correlation/idempotency keys, not entity identities. CLI and MCP expose creation operations so skills do not mint IDs themselves. UI lists and headings use existing short titles/goals/statements, with IDs available as reference details.

## Migration and integration

Provide a one-time explicit migration to the new format. No runtime fallback for old numbered IDs. Resolve references, collection paths and prose links consistently; do not run global untyped substitutions that conflate independent entities. Shared records from the common ancestor retain one mapped identity. Independently created records on each branch receive different identities even when their old ID is identical. Conflicting edits to the same common-ancestor entity require explicit semantic reconciliation; neither branch is silently preferred. Freeze the per-origin mapping in the staged migration manifest before publication so retries after interruption reuse the same mapping. Bring both feature implementations and both histories into the PR.

Persist a migration manifest with origin commits, per-origin identity mapping and original artifact hashes. Preserve original evidence/provenance in Git and the manifest; transformed historical records must not impersonate fresh execution or user approval. Snapshot/reference hashes affected by the authorized transformation are regenerated by migration code with explicit provenance. Historical run source identities remain historical; fresh tests, reviews and screenshot coverage establish current proof. Fail on ambiguous or dangling references, invalid paths or partial migrations. Stage/validate before replacing live data, support safe retry, and keep a recoverable original checkout.

## Publishing

Use an organization Actions secret named NPM_TOKEN for nessalabs, available organization-wide as requested. Credentials never enter the repository, logs or PR text. The existing release-only workflow consumes this name; manual runs remain dry runs. Validate packaging and credential wiring without publishing an npm version or creating a GitHub Release in this task. npm account reauthentication requires the user's secure local input if requested by npm.

## Acceptance

1. Concurrent CLI/MCP creations, including identical titles across independent checkouts, produce distinct UUID identities and preserve every record; retries preserve one outcome. Invalid or caller-selected legacy IDs are rejected.
2. The experiment and workflow-library branches integrate with migrated, unambiguous UUID references and preserved historical provenance. Migration validates joins and is recoverable/idempotent; current tests, reviews and declared screenshot evidence pass.
3. People see short titles in navigation and work details, and can inspect both migrated workstreams with intact results and screenshots. Skills direct agents to creation operations rather than choosing counters.
4. Publishing consumes the organization credential; package dry runs and workflow validation pass without a live release. A credential requiring human reauthentication is reported separately from code completion. Existing release-only claim SL-014 is backed by workflow tests; org-secret availability and authenticated dry-run observations are separate recorded operational evidence, never inferred from a passing test.

## Structure and boundaries

The ledger package owns UUID validation/allocation and migration. Domain writers own creation and immutable publication; application operations own retries and authorization. CLI/MCP adapt the same operations; client/server keep read semantics and UI imports client only. The migration is an explicit offline tool removable after conversion, not a compatibility layer in every reader.

## Validation

Independent spec review before build and code review after implementation. Unit/integration tests for creation, references, collision recovery, migration failure/retry and stale evidence; CLI/MCP lifecycle tests; complete build/test/verify/audit/align. Inspect desktop and mobile work lists/details and both integrated feature views. No invented passing bindings or restamped historical success.
